# RPG Maker MZ format research

RPG Maker MZ is Tilewright's first compatibility target. It is proprietary, so
this directory records evidence and uncertainty without reproducing proprietary
application code, bundled assets, or sample-game content.

No file-format behavior is currently documented here as supported. Research
must precede implementation claims.

## Claim classifications

Every material format conclusion must use one of these labels:

- **Documented:** supported by official documentation or another authoritative
  contract, with an exact citation.
- **Observed:** directly verified in legitimate, user-owned project data or
  generated output, with the relevant version and observation recorded.
- **Inferred:** a reasoned interpretation based on evidence, but not definitively
  established.
- **Unknown:** unresolved or contradicted by available evidence.

A JSON value's apparent type is a syntax observation, not proof of its semantics,
valid range, identifier rules, ordering, or cross-file invariants.

## Evidence hierarchy

Prefer evidence in this order:

1. official documentation or an explicit vendor contract;
2. direct observation of files generated by a user-owned project;
3. controlled before/after experiments that change one editor concept;
4. inspectable runtime behavior relevant to project data;
5. multiple independent community implementations or plugin-author reports;
6. a single community claim, used as a research lead rather than proof.

Community material can corroborate a conclusion but does not automatically
define Tilewright's format contract.

## Research workflow

1. State one exact question and the product behavior that depends on it.
2. Search existing research, ADRs, source, tests, and fixtures.
3. Add an entry to the [research ledger](research-ledger.md).
4. Separate observed syntax from proposed meaning and invariants.
5. Record version, unknown-field, ordering, identifier, encoding, and cross-file
   reference risks.
6. Design the smallest controlled experiment that could resolve each important
   unknown.
7. Add only legally redistributable, minimal fixtures with the provenance
   required by [`fixtures/README.md`](../../../fixtures/README.md).
8. Recommend a library contract only for behavior the evidence supports.

When evidence is incomplete, prefer lossless parsing, raw extension data,
read-only behavior, or a refused write over invented certainty.

## Evidence handling

- Cite an official page by title, URL, and access date; do not paste long
  copyrighted passages.
- Identify an observation by editor/runtime version, controlled action, and a
  sanitized fixture or reproducible procedure.
- Do not commit personal project paths, proprietary application source, vendor
  assets, default databases, sample projects, or commercial plugin content.
- Summarize runtime behavior rather than copying proprietary code.
- Record conflicting observations instead of selecting the convenient one.
- Give confidence a short rationale; do not use a numeric score as a substitute
  for evidence.

## Planned research areas

Documents may be added as evidence accumulates for:

- project layout and project detection;
- data-file inventory and version differences;
- `System.json` and `MapInfos.json`;
- maps, events, pages, and event commands;
- database files and cross-file references;
- plugin and extension fields; and
- serialization and round-trip fidelity.

Do not create an empty document merely to fill this list. A focused ledger entry
or document should exist when there is evidence to preserve.
